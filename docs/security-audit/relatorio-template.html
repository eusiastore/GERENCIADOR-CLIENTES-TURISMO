📌 Nota Metodológica e Mapeamento da Stack

A auditoria avaliou a base de código do TrevoTour cobrindo cinco categorias fundamentais de segurança adaptadas à stack real do projeto (PHP 8.2 puro com PDO, MySQL 8.0, React 18 / Vite SPA e Sessões Nativas PHP com Cookies HttpOnly):

  • 1. Banco sem Tranca (Isolamento): Validação de modelo Single-Tenant e rastreabilidade/propriedade de registros operacionais.
  • 2. Permissão Definida no Navegador: Confronto entre ocultação de UI no React e validação de Auth::requireRole('admin') nos controladores PHP.
  • 3. IDOR: Verificação de manipulação arbitrária de IDs em rotas de atualização/deleção.
  • 4. Chaves Expostas (Hardcode): Identificação de senhas de banco fixas no código, logs em disco e mensagens de debug expostas.
  • 5. Inputs sem Tratamento (XSS / SQLi): Inspeção de JSX, interpolação de queries SQL e escape de saídas.

🛡️ Pontos Fortes Verificados

  • Barreira Zero-Trust Central: api/index.php bloqueia 100% das rotas sem autenticação via Auth::requireAuth().
  • RBAC Seguro em Usuários: UsuarioController.php valida Auth::requireRole('admin') para criação e exclusão.
  • Proteção Nativa XSS: React JSX escapa automaticamente variáveis no DOM sem dangerouslySetInnerHTML.
  • Sanitização em WhatsApp: AbaPassageiros.jsx aplica regex \D impedindo esquemas javascript:.

⚠️ Principais Riscos e Fragilidades

  • Exclusão de Viagens sem Gate Admin: Operadores comuns podem disparar DELETE /?resource=viagens&id=X e apagar viagens em cascata.
  • Credenciais de Banco em Código: Senha do MySQL gravada em api/config/database.php e update_db.cjs.
  • Log de Debug Aberto em Disco: ViagemController.php grava payloads em log_update.txt acessível via HTTP.
  • Interpolação SQL em Array: PassageiroController.php concatena IDs diretamente na query SQL.

🔍 Detalhamento Técnico dos Achados

1. Exclusão de Viagens Permitida para Operadores Comuns ALTA
Arquivo & Linha: api/controllers/ViagemController.php:196-200
Categoria: Permissão Definida no Navegador / Falta de RBAC no Servidor
// api/controllers/ViagemController.php (Linhas 196-200) public function destroy(int $id): void { $stmt = $this->db->prepare("DELETE FROM viagens WHERE id = ?"); $stmt->execute([$id]); jsonResponse(true, null, 'Viagem excluída com sucesso'); }

Por que é explorável: Qualquer usuário com perfil usuario autenticado na API pode enviar uma requisição HTTP DELETE para /?resource=viagens&id=X. Como o método não executa Auth::requireRole('admin'), o registro é deletado no banco em cascata, apagando passageiros, parcelas e históricos vinculados.

2. Credenciais de Banco de Dados Hardcoded ALTA
Arquivo & Linha: api/config/database.php:8-13 e frontend/update_db.cjs:3

Por que é explorável: A senha de produção/desenvolvimento do banco está fixada no repositório. Em caso de commit público ou vazamento do código-fonte, o invasor obtém credenciais diretas do MySQL.

Arquivo & Linha: api/controllers/PassageiroController.php:31-36

--- ISSUE 1 --- 
### Título: [Segurança] Bloquear exclusão de viagens por usuários sem perfil Administrador

**Labels:** `security`, `severity: high`, `backend`, `rbac`

#### Descrição do Problema
O endpoint de exclusão de viagens (`DELETE /?resource=viagens&id=X`) não valida se o usuário autenticado possui o cargo de `admin`. Usuários com papel de operador comum (`role = 'usuario'`) conseguem invocar a rota diretamente e apagar excursões inteiras do banco de dados, excluindo passageiros e histórico em cascata.

#### Evidência
- **Arquivo:** `api/controllers/ViagemController.php:196-200`
```php
public function destroy(int $id): void {
    $stmt = $this->db->prepare("DELETE FROM viagens WHERE id = ?");
    $stmt->execute([$id]);
    jsonResponse(true, null, 'Viagem excluída com sucesso');
}
```

#### Impacto
Perda irreversível de dados operacionais e financeiros da agência por ação indevida ou maliciosa de contas não privilegiadas.

#### Sugestão de Correção
Adicionar a chamada `Auth::requireRole('admin');` no início dos métodos `destroy()` de `ViagemController.php`, `DespesaController.php` e `ClienteController.php`.

#### Critérios de Aceite
- [ ] Requisição `DELETE /?resource=viagens&id=X` com usuário `role: 'usuario'` retorna HTTP 403 Forbidden.
- [ ] Requisição `DELETE /?resource=viagens&id=X` com usuário `role: 'admin'` executa a exclusão normalmente.
--- FIM ISSUE 1 ---
--- ISSUE 2 --- 
### Título: [Segurança] Mover credenciais de banco de dados para variáveis de ambiente (.env)

**Labels:** `security`, `severity: high`, `configuration`, `hardening`

#### Descrição do Problema
As credenciais de conexão ao MySQL estão fixadas no código-fonte em texto plano nos arquivos `api/config/database.php` e `frontend/update_db.cjs`.

#### Evidência
- **Arquivo:** `api/config/database.php:8-13`
```php
define('DB_HOST', '127.0.0.1');
define('DB_USER', 'trevotour');
define('DB_PASS', 'trevotour123');
```

#### Impacto
Vazamento de credenciais do banco de dados caso o código seja commitado em repositório público ou compartilhado com terceiros.

#### Sugestão de Correção
1. Carregar variáveis via `$_ENV` ou arquivo `.env` fora do versionamento (`.gitignore`).
2. Implementar fallback seguro e validação de inicialização que rejeite senhas vazias em produção.

#### Critérios de Aceite
- [ ] Nenhuma senha em texto claro presente em arquivos PHP ou JS versionados.
- [ ] Arquivo `.env.example` fornecido como modelo para o time.

**Labels:** `security`, `severity: medium`, `privacy`, `information-disclosure`

--- ISSUE 4 --- 
### Título: [Segurança] Substituir interpolação direta de array por prepared statements em PassageiroController

**Labels:** `security`, `severity: low`, `database`, `code-quality`

#### Descrição do Problema
O método `byViagem` em `PassageiroController.php` concatena a variável `$ids` diretamente no corpo da query SQL executada via `PDO::query()`.

#### Evidência
- **Arquivo:** `api/controllers/PassageiroController.php:31-36`
```php
$ids = implode(',', array_column($passageiros, 'id'));
$parcStmt = $this->db->query("SELECT * FROM parcelas_passageiro WHERE passageiro_id IN ({$ids})");
```

#### Impacto
Violação do padrão de segurança de prepared statements e risco potencial em manutenções futuras.

#### Sugestão de Correção
Gerar placeholders dinâmicos `implode(',', array_fill(0, count($idsArray), '?'))` e executar com `$parcStmt->execute($idsArray)`.

#### Critérios de Aceite
- [ ] Todas as consultas SQL utilizam `PDO::prepare()` com binding de parâmetros.
